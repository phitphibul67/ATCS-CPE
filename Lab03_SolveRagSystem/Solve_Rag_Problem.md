1.Hallucinate problem:
-วิเคราะปัญหา: เมื่อผู้ใช้ถามคำถามที่อยู่นอกเหนือขอบเขตของฐานความรู้และตัวโมเดลจะทำการเดาคำตอบขึ้นมาเองโดยไม่มีข้อมูลอ้างอิง 
-สาเหตุ: เนื่องจากฟังก์ชันคำนวณคำตอบ (bad_generate) ขาดเงื่อนไขตรวจสอบว่ามี Context ที่ดึงมาและขาดข้อกำหนดใน Prompt ที่บังคับให้โมเดลตอบเฉพาะข้อมูลที่มีอยู่ใน Context เท่านั้น
-วิธีการตรวจสอบ: ทดสอบส่ง Query นอกขอบเขต เช่น "ตั๋วเครื่องบินไปเชียงใหม่ราคาเท่าไหร่" แล้วตรวจสอบว่าระบบส่งคืนคำตอบสุ่ม/สร้างขึ้นเองหรือไม่  
-แนวทางการแก้ไข: ปรับแก้การสร้างคำตอบในฟังก์ชัน grounded_generate โดยเช็คว่าหาก context เป็นค่าว่าง (not context) ให้คืนค่าข้อความแจ้งเตือนผู้ใช้ทันทีว่า "ไม่พบข้อมูลที่สนับสนุนคำตอบใน Knowledge Base" เพื่อยับยั้งการ Hallucination

2.tranformer problem: 
-วิเคราะห์ปัญหา: การดึงข้อมูลด้วยเทคนิค Bag-of-Words (BoW) หรือ Keyword Match ไม่สามารถจับคู่คำถามภาษากับเอกสารที่มีความหมายเดียวกันได้ หากผู้ใช้ใช้คำแสลงหรือคำไม่เป็นทางการ และไม่สามารถแยกแยะความหมายที่เปลี่ยนไปตามลำดับคำได้  
-สาเหตุ: เทคนิค BoW ตรวจสอบเฉพาะการซ้ำกันของ Exact Token (เช่น เปรียบเทียบคำถามทางการกับคำถามแสลงเรื่องถุงยางอนามัย) และละทิ้งโครงสร้างตำแหน่ง (Positional Information)  
-วิธีการตรวจสอบ: เปรียบเทียบค่า Token Overlap ระหว่างคำถามภาษากับคำถามทางการ หรือเปรียบเทียบการสลับลำดับคำในประโยคเดิมแล้วเช็คค่า BoW Vector  
-แนวทางการแก้ไข: เปลี่ยนไปใช้ Transformer ร่วมกับ Dense Embedding ที่มีเทคนิค Positional Encoding และ Self-Attention mechanism เพื่อรักษาลำดับคำและจับความหมายในระดับ Semantic ทำให้รับมือกับภาษาแสลง/ภาษาทางการได้

3.Data quality problem:
-วิเคราะห์ปัญหา: พบข้อมูลซ้ำซ้อน (Duplicates), ข้อมูลขยะ (Noise) เช่น สัญลักษณ์พิเศษ !, _ และเว้นวรรคส่วนเกิน ซึ่งส่งผลให้ Vector Database จัดเก็บข้อมูลอย่างไม่เป็นระเบียบและทำให้ดึงข้อมูลคลาดเคลื่อน  
-สาเหตุ: กระบวนการนำเข้าข้อมูล (Data Ingestion/Scraping) ขาดขั้นตอนการฟอกข้อมูล (Data Normalization & Cleaning)  
-วิธีการตรวจสอบ: เขียนฟังก์ชันสแกนตรวจสอบข้อมูลใน sex_q_a.txt เพื่อหาชุดข้อมูลซ้ำซ้อนหลังการแปลงรูปแบบ เช่น ลบสัญลักษณ์และแปลงเป็นตัวพิมพ์เล็ก  
-แนวทางการแก้ไข: เขียนฟังก์ชัน normalize() ใช้ Regular Expression ในการคลีนข้อมูล (re.sub(r"[_@!\-]+", " ", text)) ทำการลบเว้นวรรคส่วนเกิน แปลงเป็นข้อความตัวพิมพ์เล็ก และตัดรายการที่ซ้ำกันออกด้วย list(dict.fromkeys(...)) ก่อนนำไปทำ Indexing  

4.Chunking problem:
-วิเคราะห์ปัญหา: Chunk ขนาดใหญ่เกินไปเพราะนำหลายคำถาม-คำตอบมารวมกัน ทำให้ Embedding โดนเจือจาง (Diluted) และหาก Chunk ขนาดเล็กเกินไป ข้อความขาดออกจากกันกลางประโยค บริบทความหมายสูญหาย  
-สาเหตุ: การกำหนดจุดตัดแบ่งข้อความ (Split Point) ไม่สัมพันธ์กับโครงสร้างเนื้อหา  
-วิธีการตรวจสอบ: สุ่มดึงข้อความจากการแบ่ง Chunk หลายๆ ขนาด (เช่น 200 คำ และ 15 คำ) แล้วตรวจสอบความสมบูรณ์ของประโยค  
-แนวทางการแก้ไข: ใช้เทคนิค Chunking + Overlap (เช่น กำหนด size=60, overlap=15) เพื่อสร้างพื้นที่คาบเกี่ยวระหว่างข้อความ ช่วยรักษาบริบทตรงจุดเชื่อมต่อเอกสารไม่ให้ขาดออกจากกัน  

5.Meta data problem:
วิเคราะห์ปัญหา: การดึงข้อมูลคืนค่าเอกสารที่มีคำสำคัญตรงกัน แต่ระดับภาษา (Tone/Register) ไม่เหมาะสมกับการนำไปใช้งาน (เช่น ได้คำตอบภาษาแสลงในแชทบอททางการแพทย์)  
-สาเหตุ: ระบบใช้การค้นหาเฉพาะ Similarity Score เพียงอย่างเดียว โดยไม่ได้คัดกรอง Metadata เช่น lang (ทางการ/ภาษาพูด/แสลง)  
-วิธีการตรวจสอบ: ค้นหาคำถาม "ถุงยาง หลุด ทำไง" แบบไม่ใส่ Filter และเปรียบเทียบผลลัพธ์กับแบบใส่ Filter lang='ทางการ'  
-แนวทางการแก้ไข: เพิ่มกระบวนการ Metadata Filtering ในฟังก์ชัน search() โดยกำหนดเงื่อนไขคัดกรองแท็ก lang (เช่น lang="ทางการ") ควบคู่ไปกับการทำ Similarity Search  

6.reranking problem:
-วิเคราะห์ปัญหา: เอกสารที่ตรงกับคำตอบที่สุดถูกจัดอยู่อันดับล่างๆ ในขั้นตอนแรกของการดึงข้อมูล (First-stage Retrieval)  -สาเหตุ: การดึงข้อมูลขั้นแรกให้น้ำหนักกับคำทั่วไป (Generic terms เช่น "เอชไอวี", "ตรวจ") เท่ากับคำเฉพาะเจาะจง (Specific terms)  
-วิธีการตรวจสอบ: ตรวจสอบ Ranking ของเอกสารจากการดึงข้อมูลรอบแรก (Top-k) แล้วดูว่าคำตอบเฉพาะเรื่อง (เช่น "ระยะฟักตัว") ติดอยู่อันดับล่างหรือไม่  
-แนวทางการแก้ไข: เพิ่มกระบวนการ Re-ranking (Two-stage Retrieval) หลังดึง Top-k โดยคำนวณคะแนนใหม่ด้วยฟังก์ชัน rerank() เพิ่มน้ำหนัก (Extra Weight) ให้กับคำศัพท์เฉพาะเจาะจง เพื่อดันเอกสารที่เกี่ยวข้องจริงขึ้นมาอยู่อันดับต้น

7.Generation problem:
-วิเคราะห์ปัญหา: ข้อมูลที่ดึงมา (Retrieval) ถูกต้องแล้ว แต่ตัวโมเดลสร้างคำตอบ (Generator) บิดเบือนตัวเลขหรือข้อมูลสำคัญ เช่น สลับระยะเวลาการกินยา PEP  
-สาเหตุ: โมเดล LLM ใช้ความรู้เดิมที่เคยถูก Train มาในการตอบคำตอบ หรือสูญเสียความแม่นยำในการอ้างอิง Context (ตัวอย่างเช่น เปลี่ยนจาก "72 ชั่วโมง" เป็น "7 วัน")  
-วิธีการตรวจสอบ: เปรียบเทียบข้อความใน Context ที่ดึงมากับผลลัพธ์จากฟังก์ชัน bad_generator()  
-แนวทางการแก้ไข: ปรับ Prompt ให้บังคับโมเดลตอบเฉพาะข้อมูลจาก Context (Grounded Generation) เท่านั้น และทำการประเมินความถูกต้อง (Faithfulness Evaluation) ก่อนส่งคำตอบออกไป  

8.Config, evsluation and debug scripts problem:
-วิเคราะห์ปัญหา: Performance ของระบบ RAG ต่ำเกินไปหรือไม่สม่ำเสมอ  
-สาเหตุ: ขาดการเปิด-ปิดส่วนประกอบ (Components) ให้เหมาะสม เช่น ขาด Re-ranking, ขาด Hybrid Search หรือไม่มีสคริปต์สำหรับการประเมินผลและการ Debug  
-แนวทางการแก้ไข:ออกแบบตาราง/ดิคชันนารีสถาปัตยกรรม RAG ควบคุมด้วย CONFIG สามารถสลับโหมดการทำงาน เช่น USE_HYBRID, USE_RERANK, USE_MEMORY ได้อย่างยืดหยุ่น  สร้างสคริปต์ประเมินผล (Evaluation) เพื่อวัดค่า Recall/Precision ของ Chunk และสคริปต์ Debug เพื่อตรวจสอบ Pipeline การทำงานแบบละเอียด
